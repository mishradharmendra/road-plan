# Principal Java Architect — Risk Intelligence Division

Onboarding, roadmap, and measurement kit for a **Principal Java Architect** joining the
**Risk Intelligence** division of a large financial firm.

## Context assumptions baked into this kit

| Dimension | Assumption |
|---|---|
| Domain | Risk Intelligence — market/credit risk, VaR, stress & scenario, limits/exposure, surveillance/AML/fraud, regulatory reporting (FRTB, Basel, CCAR/DFAST, BCBS 239) |
| Tech surface | JVM platform: risk compute/grid, streaming enrichment, data serving APIs, batch orchestration |
| Org size | Large division, many solution engineers, multiple delivery teams |
| Peer principals | Principal AI, Principal Web Engineer (peers, **not** reports) |
| Base location | India |
| Distribution | Part of the org sits outside India (US / UK / APAC) |
| Role type | New hire, no existing internal capital |

## How each roadmap file is structured

Every roadmap file uses the same four-part frame:

1. **Questions to ask** — the literal question, the audience, and *what answer you actually want*
2. **Actions / TODO** — concrete, time-boxed work
3. **Metrics to capture** — what you instrument or baseline in that phase
4. **Outcomes to produce** — the named artifacts that must exist at the end of the phase

## Guiding principle

> Authority in a principal role is granted by peers, not by title — especially when you are
> remote from part of the org. For the first 90 days, be the person who understands the
> domain most deeply and takes the least credit.
